# Jev Relationship Assistant Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add encrypted local history, user-controlled relationship memory, and clean extension seams for accessibility and floating assistant surfaces.

**Architecture:** Keep Conversation, Analysis, Contact, and Relationship Memory in the domain layer. Room adapters persist encrypted history and contact observations; `ConversationSource` and `AssistantSurface` are explicit interfaces so future AccessibilityService and overlay code cannot bypass consent or the existing analysis use case.

**Tech Stack:** Existing Jev MVP stack plus SQLCipher for Android/Room and Android AccessibilityService/WindowManager contracts.

**Spec:** `docs/superpowers/specs/2026-09-21-jev-mvp-design.md`, `CONTEXT.md`, `docs/adr/0001-encrypted-local-history.md`

## Global Constraints

- Conversation history remains local-only unless the privacy consent flow is confirmed.
- API keys and database passphrases are protected by Android Keystore-backed AES-GCM.
- Relationship Memory is editable user data, not an unverified psychological diagnosis.
- Accessibility and overlay features are opt-in and disabled by default.
- No feature may send or post a message automatically.
- Jev analysis must use typed Choice/Score/Noul decisions; do not parse generated prose as the analysis contract.
