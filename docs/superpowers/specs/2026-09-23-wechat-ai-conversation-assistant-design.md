# 微信聊天内 AI 整体分析与连续问答设计

**日期：** 2026-09-23  
**状态：** 已确认并实现  
**范围：** 微信 8.0.72 / versionCode 3085 的 Xposed 集成

## 目标

在微信聊天标题栏添加“AI分析”按钮。点击后，在当前聊天界面中央打开可滚动的 Jev 对话框。理解模型读取当前会话最新的完整本地文本记录，生成整体梗概和对方表达意思的说明，并允许用户继续追问。

会话按微信内部会话 ID 区分。再次打开同一聊天时沿用已保存的模型问答，但每次生成报告或回答追问前都重新读取最新聊天文本。单聊和群聊各自保留独立问答。对话框关闭后回到原微信聊天。

## 现有基础

- Xposed 已在微信聊天标题栏放置 `Jev` 实时卡片开关，并通过配对过的 Messenger IPC 与 Jev 主 App 通信。
- 微信进程侧的 `WechatLocalHistoryReader` 可从当前 `Chat_User` 读取本地 `message` 表；`LocalHistoryBroker` 分页返回完整文本记录，并校验请求仍对应当前会话。
- 主 App 使用 SQLCipher/Room 加密数据库；数据库当前为 version 3。
- “理解模型”通过主 App 中的 OpenAI 兼容客户端和独立 reply/understanding provider 配置调用。现有调用只接受单轮 system/user prompt，没有连续聊天接口。
- 微信侧消息行、气泡和头像继续由微信自己渲染；新报告不插入成逐条消息卡片。

## 方案选择

使用微信进程内的居中 `Dialog` 承载 UI，模型和会话数据仍由 Jev 主 App 负责。Xposed 侧只管理当前 Activity、按钮、对话框和 IPC 回调；它不直接读取 Jev 数据库或调用外部模型。

全屏 Jev Activity 易于复用 Compose，但会切换离开微信；在微信进程内绘制完整问答组件会让模型、存储与 UI 都耦合进 Xposed。居中 Dialog 符合当前确认的交互，同时以 IPC 保持 Xposed 端轻量。

## 交互

1. 标题栏在现有 `Jev` 开关旁显示“AI分析”按钮。它是按需功能，不随实时逐条分析开关关闭。
2. 点击后立即创建居中、圆角、最大约屏幕宽度 92%、高度 88% 的 Dialog，显示加载态；保留暗色遮罩和微信底层聊天。Dialog 包含标题/关闭按钮、可滚动报告与问答列表、底部多行输入框和发送按钮，键盘弹出时输入区保持可用。
3. 若该聊天没有已保存会话，主 App 请求理解模型生成首次整体报告。若已有会话，则把此前的 user/assistant turns 一并带入模型，在同一会话中生成基于最新聊天内容的更新报告。
4. 用户每次发送追问时，主 App 重新读取完整本地聊天记录，将最新聊天文本和该会话保存的问答历史共同发给理解模型。回答返回后追加到 Dialog 并持久保存。
5. “关闭”只关闭 Dialog，不清除会话；下次打开继续显示同一聊天的问答。实时卡片的 Jev 开关与此功能相互独立。

报告至少包含：聊天内容梗概、对方主要想表达或希望得到什么、依据原文的关键点、目前仍不确定之处，以及可以礼貌确认的问题。Prompt 要求模型区分文本证据与推测，不做心理或医学诊断，不编造聊天中没有的事实。用户追问按普通自然语言回答。

## 架构和数据流

### 微信/Xposed 侧

- 在 `WechatChatUiHook` 标题栏安装“AI分析”按钮，并从当前 fragment 取得 Activity context 创建/关闭 Dialog。
- Dialog 的报告和问答区由专用 `ChatAssistantDialog` 组件负责，提供 loading、内容追加、失败重试、发送中禁用和键盘/滚动行为。
- `JevIpcClient` 增加经过现有配对认证的 assistant request 发送方法，并将 requestId 对应的结果回调给 Dialog。关闭窗口或 Activity 销毁时解绑该请求，避免结果更新失效视图。
- 请求只包含 requestId、会话 ID、标题和可选用户问题；完整聊天文本仍从微信侧本地数据库按现有 history IPC 读取，不在按钮 View 中缓存或写日志。
- Dialog 与聊天同属微信 Activity，不触发 `onPause`，现有本地记录 reader 可以继续验证 `Chat_User` 并读取最新记录。

### Jev 主 App 侧

- 扩展 IPC 协议，增加打开报告/提交追问请求和关联结果类型；服务端仅接受已认证的微信 Messenger 客户端，并校验请求 ID、会话 ID、文本长度和角色。
- 新增 `ChatAssistantCoordinator` 处理并发、忙碌状态、错误返回和取消；每个请求先通过 `LocalHistoryBroker.load(conversationId, title)` 拉取最新文本记录，再读取同一会话的持久化 turns，组装 prompt 并调用 configured understanding provider。
- 首次打开插入一条用于整体分析的用户 turn，并保存模型报告为 assistant turn。已有会话再次打开时插入“请基于最新聊天内容更新整体分析”的请求，同会话继续。后续用户问句和模型回答成对追加。
- 每次模型请求的消息顺序为：固定安全规则 system prompt、最新本地聊天上下文（system context）、已有持久化问答 turns、当前自动报告请求或用户问题。最新聊天上下文每次刷新，不作为重复的旧 user turn 堆积。
- 使用 `OpenAiCompatibleClient` 的理解模型配置，不调用每条消息的概率分析管道，也不改变实时卡片生成行为。

### 持久化

- Room schema 升级到 version 4，沿用现有 SQLCipher 数据库。
- 新增 `chat_assistant_sessions`：`conversationId` 为主键，保存展示标题、创建和更新时间。
- 新增 `chat_assistant_turns`：自增 ID、会话 ID、`user`/`assistant` role、文本和创建时间；对 session 建立外键级联删除和按 `(conversationId, id)` 的索引。
- 只持久化 user/assistant 问答；最新微信聊天文本作为每次请求的短期上下文，不复制进问答历史表。现有数据库加密仍保护本地问答。
- 不提供新建/删除会话控件；“沿用之前会话”是本次目标，清理功能留待后续明确需求。

## 错误处理与隐私

- 无理解模型配置、模型调用失败、历史读取失败、会话切换或 IPC 断开时，在 Dialog 显示可读错误和重试入口；禁止静默改用可见屏幕片段、旧上下文或演示模型。
- 历史读取严格要求所请求 `conversationId` 与微信当前打开会话一致。会话切换后旧结果以 requestId 丢弃，不展示到新聊天。
- 不记录消息正文、问句、prompt、模型回答或密钥到日志。
- 按钮及 Dialog 文字明确提示：整体本地聊天文本会发送到当前配置的理解模型；发送只由用户点击“AI分析”或发送追问触发。
- 微信撤回提示和系统行沿用 `ChatTextPolicy` 过滤；本地 history 查询仍仅包含普通文本消息。
- OpenAI 兼容服务上下文长度可能小于微信全量本地文本上限。若完整文本超出模型/API 接受范围，显示错误供用户处理，不静默截断或伪称已分析全部上下文。
- 对话框关闭、聊天切换或连接断开时取消当前请求；同一聊天启动新请求前取消旧任务。若 IPC 请求解码失败但请求 ID 与聊天 ID 合法，立即返回关联错误。

## 验证

- Domain/Room 测试：首次整体报告写入 session；按 conversation ID 隔离；重开复用已有 turns；每次请求收到最新文本上下文；失败后不留下半条问答；迁移保留旧版分析和缓存表。
- IPC 测试：请求及结果序列化、ID 关联、未经认证请求拒绝、切换会话时过期结果丢弃、长度边界和断连状态。
- Prompt/API 测试：system 规则、最新聊天上下文、历史 turns 和本轮问题顺序正确；只调用配置的 understanding provider。
- UI 测试：按钮状态、居中 Dialog 内容、加载/失败/重试、连续问答展示、关闭和 Activity 销毁清理。
- 真机验收微信 8.0.72：聊天标题栏按钮位置；单聊和群聊独立会话；报告在居中 Dialog 中；追问使用最新本地聊天记录；关闭重开沿用问答；原实时卡片开关仍独立工作。

## 验收条件

- 点击“AI分析”在原微信聊天上方打开居中 Dialog，生成整段聊天梗概和对方意图报告。
- Dialog 中可用自然语言继续提问，回复接续之前的同聊天问答。
- 新的报告或问题始终重新读取最新本地文本；此前的 AI 问答历史会带入理解模型。
- 单聊和群聊 session 不串线；用户关闭窗口后再打开能恢复历史问答。
- 历史读取/模型/IPC 失败不会把旧聊天内容或错误会话结果展示到当前窗口。
- 自动逐条卡片、其缓存、撤回过滤和已有微信原生布局行为不受影响。
